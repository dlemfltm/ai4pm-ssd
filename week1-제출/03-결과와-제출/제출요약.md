## 무엇을 / 왜 만들었나

- **무엇**: 더미 예상손익 자료(입력 명세 · 차이 규칙)를 LLM Wiki로 가공한 팀 지식 1세트.
- **왜**: PM·재무 담당자가 계획 대비 실적을 점검하는 예상손익 보고서를, AI가 근거 있게 다시 만들 수 있도록 준비하기 위해.

## 배운 점 (과제를 직접 진행하며)

- **가장 어려웠던 건 '찾기'가 아니라 '선별'이었다.** 자료를 모으는 것보다, 모은 것 중 무엇을 남기고 무엇을 버릴지 판단하는 게 힘들었다. 그래서 다 넣지 않고 프로젝트 질문에 답하는 자료만 남기고, 확인 전에는 전부 '후보'로 표시하는 기준을 세웠다.
- **AI에게 맡길 것과 내가 정할 것이 분명히 갈렸다.** 계산·정리·초안 같은 가공은 AI에게 맡길 수 있었지만, 차이 '큼'의 임계값이나 최종 승인처럼 **근거가 없는 판단은 임의로 채우지 않고** `needs-review`로 남겨 사람이 정하도록 했다. (가공은 AI, 확인은 사람)
- **답보다 '근거 위치'가 중요했다.** 그냥 답만 받는 게 아니라, 어디에 근거했는지(원문 SRC 번호·절)까지 남겨야 나중에 신뢰하고 다시 쓸 수 있다는 걸 알았다.
- **쌓는 자료가 아니라 '다음 사람이 쓰는' 자료.** 같은 서식(한 줄 요약·근거·사용처·확인 상태)으로 정리하니, 다른 팀원이 한 페이지만 봐도 쓸 수 있는 형태가 됐다.
- **원본은 건드리지 않는다.** 원문은 `raw/`에 그대로 두고 가공본만 `wiki/`에 따로 만들어, 원본을 훼손하지 않으면서 재사용 가능한 형태로 남겼다.

## 적용한 작업 원칙

- 넓은 요청을 바로 검색하지 않고 **개발 질문 5개**로 쪼갠다 → 자료는 확인 전까지 "후보".
- 자료는 **신뢰도 순서**(공식·승인 → 담당자확인 → 블로그·AI)로 읽고, 대장(`vault/wiki/자료대장.md`)에 등재·집계·판정(`확인한-자료.md`).
- AI에게 넘기기 전 **5가지 거르기**, 모든 자료에 **가공 기준 4가지**(한 줄 결론 · 근거 위치 · 사용처 · 확인 상태) 적용.
- 위키는 **3층 구조**(CLAUDE.md / wiki / raw), 원문 1건은 **6단계**로 가공, **1건씩** 처리.
